CI/CD GitHub Actionsilla

< Takaisin etusivulle

1. Mitä CI/CD tarkoittaa?

CI eli Continuous Integration tarkoittaa, että koodimuutokset tarkistetaan automaattisesti aina, kun ne pushataan repositoryyn tai niistä tehdään pull request. CD eli Continuous Delivery tai Deployment tarkoittaa, että hyväksytty muutos voidaan paketoida ja julkaista hallitusti.

Tässä projektissa CI/CD toteutetaan GitHub Actionsilla. Workflow-tiedosto on .github/workflows/ci.yml, ja se tarkistaa Python-koodin, testit, Compose-määrityksen, Node.js-sovelluksen, Docker-imaget sekä Terraform-tiedostot.

2. Milloin pipeline käynnistyy?

Workflow käynnistyy push- ja pull_request-tapahtumista. Lisäksi workflow tarkkailee vain projektin kannalta olennaisia polkuja, kuten healthcheck/, tests/, notes-api/, web/, proxy/, docker-compose.yaml ja terraformlearnerlab/.

on:
  push:
    paths:
      - "notes-api/**"
      - "web/**"
      - "docker-compose.yaml"
  pull_request:
    paths:
      - "notes-api/**"
      - "web/**"
      - "docker-compose.yaml"

Path-suodatus vähentää turhia ajoja: workflow ei käynnisty muutoksista, jotka eivät vaikuta tarkistettaviin osiin.

3. Lint ja Python-testit

lint-job asentaa Python 3.12:n ja suorittaa Ruff-tarkistuksen:

ruff check healthcheck tests

Lint tarkistaa Python-koodin tyylin ja yleisiä ohjelmointivirheitä ilman, että sovellusta tarvitsee käynnistää.

test-job asentaa projektin ja testiriippuvuudet ja suorittaa yksikkötestit:

python -m pip install --upgrade pip
python -m pip install -e . pytest
pytest -v

Testit sijaitsevat tests/-kansiossa ja testaavat healthcheck-paketin toimintaa, mukaan lukien raja-arvotapauksia.

4. Python-paketin rakentaminen

package-job käynnistyy vasta, kun sekä lint että testit ovat onnistuneet:

needs: [lint, test]

Job rakentaa lähdejakelun ja wheel-paketin:

python -m pip install --upgrade pip build
python -m build

Rakennetut dist/*.whl- ja dist/*.tar.gz-tiedostot tallennetaan GitHub Actionsin artefaktiksi nimellä healthcheck-<commit-sha>. Artefakti säilytetään 14 päivää.

5. Compose-pinon ja Node.js:n tarkistukset

stack-job tarkistaa, että projektin Compose-määritys on kelvollinen:

docker compose config -q

Komento validoi docker-compose.yaml-tiedoston ilman, että koko pinoa tarvitsee käynnistää.

Samassa jobissa tarkistetaan API:n JavaScript-syntaksi ja riippuvuudet:

node --check notes-api/server.js

cd notes-api
npm install --no-audit --no-fund

Näin CI havaitsee syntaksivirheet ja riippuvuuksien asennusongelmat ennen kuin sovellusta yritetään ajaa Dockerissa.

6. Docker-imagien rakentaminen

images-job rakentaa projektin omat imaget:

docker build -t web-ci ./web
docker build -t notes-api-ci ./notes-api

Tämä tarkistaa, että [web/Dockerfile](/home/aleks/docker-rojekti/web/Dockerfile) ja [notes-api/Dockerfile](/home/aleks/docker-rojekti/notes-api/Dockerfile) toimivat CI-ympäristössä ja että niiden tarvitsemat tiedostot löytyvät. Imaget rakennetaan validointia varten, eikä niitä tässä jobissa julkaista Docker Hubiin.

7. Terraformin validointi

terraform-job tarkistaa terraformlearnerlab/-kansion:

terraform fmt -check -recursive
terraform init -backend=false
terraform validate
  • terraform fmt -check -recursive tarkistaa tiedostojen muotoilun.
  • terraform init -backend=false alustaa Terraformin ilman etäistä backendia.
  • terraform validate tarkistaa määritysten rakenteen ja syntaksin.

Validointi ei vielä luo AWS-resursseja.

8. Jobien riippuvuudet

Putken jobit on ketjutettu niin, että seuraava vaihe käyttää vain onnistuneen edellisen vaiheen tulosta:

package  <- lint, test
deploy   <- lint, test, package, stack, images, terraform

Deploy ei siis voi edetä, jos esimerkiksi testit epäonnistuvat, Compose-tiedosto ei ole kelvollinen, Docker-image ei rakennu tai Terraformin validointi epäonnistuu.

9. Deploy vain version tageilla

deploy-jobin ehto on:

if: startsWith(github.ref, 'refs/tags/v')

Deploy käynnistyy vain version tageilla, kuten:

v1.0.0
v1.2.3

Tavallinen push tai pull request suorittaa tarkistukset, mutta ei deployta tuotantoon.

10. AWS OIDC ja vähimmät oikeudet

Deploy käyttää GitHub Actionsin OIDC-tunnistautumista AWS:n IAM-roolin ottamiseen. Pitkäkestoisia AWS-avaimia ei tallenneta repositoryyn:

permissions:
  id-token: write
  contents: read

role-to-assume: ${{ vars.DEPLOY_ROLE_ARN }}

Workflowlla on oletuksena vain contents: read -oikeus. Deploy-job saa lisäksi id-token: write -oikeuden, koska se tarvitsee sitä lyhytkestoisen OIDC-tokenin luomiseen. IAM-roolin ARN luetaan repositoryn muuttujasta DEPLOY_ROLE_ARN.

11. Samat tarkistukset paikallisesti

Virheet kannattaa löytää jo ennen pushia. Keskeiset CI-komennot voi ajaa omalla koneella:

ruff check healthcheck tests
pytest -v
python -m build

docker compose config -q
node --check notes-api/server.js
docker build -t web-ci ./web
docker build -t notes-api-ci ./notes-api

cd terraformlearnerlab
terraform fmt -check -recursive
terraform init -backend=false
terraform validate

12. Tiivistelmä

  • GitHub Actions käynnistyy push- ja pull request -tapahtumista.
  • Ruff tarkistaa Python-koodin ja pytest suorittaa yksikkötestit.
  • Python-paketti rakennetaan ja tallennetaan artefaktiksi.
  • Compose-tiedosto, Node.js-syntaksi ja npm-riippuvuudet tarkistetaan.
  • web- ja notes-api-imaget rakennetaan CI:ssä.
  • Terraform-määritykset formatoidaan ja validoidaan.
  • Deploy odottaa kaikkien validointien onnistumista ja tapahtuu vain v*-tageilla.
  • AWS-yhteys muodostetaan avaimettomasti OIDC:n avulla.
